System design · 11 August 2026

Build the whole system first.

We will build a Slack assistant that answers HR policy questions from approved documents and refers unsafe questions to a person.

Python Slack Postgres Google Cloud

The core lesson

The model is one part of the product.

A real AI system must accept work, store it, make safe choices, use trusted data, recover from failure, and show what happened.

Status: ready for design review. No application code is approved by this document yet.

1 · Product outcome

From repeated email to one clear Slack thread.

Today

Employees email HR with the same policy questions.

HR searches documents and writes each reply by hand.

Simple questions wait beside sensitive cases.

With this system

An employee asks a general policy question in #ask-hr.

The assistant replies in the thread from an approved policy.

Off-topic, sensitive, and unsupported questions go to HR.

A successful answer

“You can carry up to five unused days into the next holiday year with manager approval.”

2 · Product boundary

A narrow job is a safer job.

Version one serves one company, one Slack workspace, and one public HR channel. It handles new top-level text messages only.

It can

  • Answer general policy questions.
  • Name the policy used.
  • Refuse unrelated questions.
  • Refer unclear or sensitive cases.
  • Keep a record of each result.

It cannot

  • Read employee records.
  • Calculate personal entitlement.
  • Approve leave or expenses.
  • Handle private cases.
  • Answer from general model knowledge.

3 · Synchronous and asynchronous work

Accept now. Think later.

Slack expects an HTTP success response within three seconds. Model calls and document checks can take longer, so they run after the event is stored.

Synchronous · under 3 seconds

Slack waits
  1. 1Check Slack's signature and timestamp.
  2. 2Validate the event shape and channel.
  3. 3Store the event, request, and queue intent in one transaction.
  4. 4Return HTTP 200 after the database commit.

Asynchronous · background

Slack is free
  1. 1A dispatcher turns the stored intent into a Cloud Task.
  2. 2One worker claims the request with a timed lease.
  3. 3The worker routes, retrieves, and checks evidence.
  4. 4A separate delivery claim controls the Slack reply.

6 · Safety design

Use a workflow, not an open agent.

The model cannot choose arbitrary tools. Application code decides which step can run and owns the fixed refusal and referral messages.

The course still teaches agent loops. The finished product uses the safer workflow because its job is narrow and the business rules are known.

7 · RAG choice

Start by loading the small trusted set.

Retrieval-augmented generation, or RAG, means adding trusted information to the model request. Version one loads every active policy because the approved collection is small.

Chosen now

Small-set loading

Load one approved active version of each policy from Postgres. Recheck those versions before delivery.

Guardrail

A hard context limit

Use the selected model's tokenizer. Stop and refer above 12,000 policy tokens. Do not estimate with character count or drop a policy.

Later

Hybrid search

Add keyword and vector search only when the policy set becomes too large. Teach that deeper path in The Vault.

Code checks proof

An exact quote proves that the source text exists. It does not prove that the claim is correct. A fixed evaluation set must test whether each answer follows from its evidence. Policy conflicts, missing evidence, and policy changes before delivery all produce a referral.

8 · Main decisions

Keep each choice easy to explain.

Deterministic workflow

Application code owns the order. We reject an open tool-using agent because the allowed paths are already known.

Cloud Tasks

One outbox row creates one worker request. We reject Pub/Sub for version one because one event does not need many consumers.

Postgres is the record

Cloud Tasks wakes the worker. Postgres owns queue intent, leases, request state, attempts, evidence, and delivery state.

Two Cloud Run services

The public ingress has a narrow job. The private worker uses IAM and owns model, database, and Slack reply access.

OpenAI Responses API

The first production path uses direct typed model calls. Framework agents remain teaching examples, not a hidden product dependency.

Private policy import

A command validates approved Markdown from a private customer source and publishes it in one transaction. Real policies never enter this public repository.

9 · Components and data

Store enough to explain each result.

The database keeps business state. Logs help operators find problems, but logs are not the source of truth.

slack_events

Slack event ID, workspace, channel, user, message time, raw body hash, and received time. The event ID is unique.

support_requests

Request ID, question text, state, route, reason, model, prompt version, usage, latency, lease owner, and lease expiry.

dispatch_outbox

Request ID, dispatch number, unique task name, state, attempts, next dispatch time, and last safe error code. It is written with the request.

outbound_deliveries

One row per request with pending, sending, sent, or uncertain, plus a delivery lease, Slack metadata ID, and Slack message time. Only pending can start a send. An expired sending lease becomes uncertain.

policy_documents

Stable policy ID, version, content, content hash, approver, approval time, and active state. A database rule permits one approved active version per policy.

answer_evidence

Request ID, policy ID, policy version, and the exact supporting quote returned by the model.

processing_attempts

Attempt number, start and end time, outcome, safe error code, and retry choice. Secrets and raw model prompts stay out of logs.

Policy publication is atomic. The import command validates every file before it changes any active version. A failed import changes nothing. Evidence keeps the exact version used. Example policies can live in this public repository. Real customer policies must come from a private approved source.

10 · Failure and recovery

A retry must not create a second answer.

Slack and Cloud Tasks both retry. Every step must therefore be safe to run again.

Duplicate event

The unique Slack event ID returns the saved result. It does not create new work.

Task creation fails

The outbox row stays pending. A private dispatcher runs each minute. Its task name combines request ID and dispatch number. ALREADY_EXISTS counts as success only for that same outbox row.

Reply result is unclear

A timeout, unclear response, process crash, or expired sending lease becomes uncertain. It never returns to pending. Reconcile the Slack thread, then require operator review if proof is missing.

Worker claim

Postgres grants one atomic 120-second lease. The worker refreshes it between steps and must finish within 90 seconds. A second worker returns success without doing work while the lease is active.

Stale work

An expired request lease is requeued while fewer than five application attempts have started. At five attempts it moves to needs_review. A request queued for 20 minutes also moves to review as an infrastructure failure.

Retry contract

The application attempt count is authoritative and stops work at five. Cloud Tasks has a 180-second deadline and only transports retries. Extra task delivery after the budget returns HTTP 204 without work.

Model failures

A route timeout or invalid route becomes a fixed referral. A temporary answer failure uses the application attempt budget. When that budget ends, the result becomes the fixed referral. Only infrastructure or referral-delivery failure reaches review.

Operator recovery

A small command-line tool lists stale requests, uncertain deliveries, failed dispatches, and failed retention runs. An operator can inspect one request, mark a proved Slack message as sent, or requeue safe work. Requeue creates a new dispatch number and task name. It never clears an active lease or changes uncertain delivery to pending.

11 · Security, privacy, and limits

Fail closed.

When identity, scope, evidence, or delivery is unclear, the system does not invent an answer.

Trust Slack carefully

Verify the HMAC signature against the raw body. Reject requests more than five minutes old.

Filter exact events

Require the configured workspace and channel, a human user, and a new top-level text message. Ignore bots, edits, deletes, files, and thread replies.

Use least access

The ingress can store requests and outbox rows. Only private services can dispatch tasks, call the model, or post to Slack.

Keep secrets out

Store tokens and API keys in Secret Manager. Never write them to Postgres, logs, or model prompts.

Delete private text

A daily private job redacts question text, answer text, and evidence quotes after 30 days. It keeps IDs, states, timings, policy versions, usage, and cost.

Know the outside copies

Logs and traces omit message content. Slack and the model provider keep data under their own policies. Production waits for customer approval of those terms.

Bound the model

At most two model calls per request. Each call has a 30-second timeout. Answers are at most 1,200 characters.

Make cost visible

Record model name, tokens, latency, and estimated cost for every completed request.

12 · Build plan

Build one proved slice at a time.

Each phase ends with something we can run, inspect, and approve. Later work depends on the gate before it.

Phase 1

Application foundation

Package, config, Postgres migrations, local commands, health checks.

Gate: a clean database can be created and checked locally.

Phase 2

Slack ingress

URL check, signature check, exact event filter, request and outbox transaction.

Gate: valid human messages are stored once; every other event shape is rejected or ignored.

Phase 3

Background work

Outbox dispatcher, Cloud Tasks adapter, atomic leases, retries, stale-work sweeper, operator requeue.

Gate: enqueue failure and duplicate workers still produce one completed request.

Phase 4

Scope and referral

Typed route decision, fixed refusal, fixed referral, failure handling.

Gate: off-topic and unsafe questions never reach answer generation.

Phase 5

Trusted policy answers

Atomic policy publication, token budget, typed claims, policy conflict and evidence checks.

Gate: every factual claim maps to active versioned evidence and passes the eval set.

Phase 6

Slack delivery

Delivery ledger, atomic delivery lease, message metadata, thread reconciliation, rate limits.

Gate: uncertain delivery never triggers an automatic second reply.

Phase 7

Evals and operations

Fixed cases, logs, traces, usage, cost, retention job, and an operator CLI for stale or uncertain work.

Gate: one run can be explained and every failed state has a tested recovery command.

Phase 8

Google Cloud deployment

Cloud Run, Cloud Tasks, Cloud Scheduler, Cloud SQL, Secret Manager, IAM, live Slack, and failure drills.

Gate: live tests cover IAM failure, enqueue failure, scheduled jobs, duplicate workers, unclear delivery, and safe recovery.

13 · Rules that must stay true

Invariants

  1. INV-1: No Slack event can create work before its signature and timestamp pass.
  2. INV-2: A valid event, request, and outbox row commit together before the ingress returns success.
  3. INV-3: One Slack event ID maps to one support request.
  4. INV-4: The model cannot call Slack, Postgres, or Cloud Tasks.
  5. INV-5: Off-topic requests do not reach retrieval or answer generation.
  6. INV-6: An invalid route, route timeout, invalid grounded result, or evidence conflict becomes a human referral.
  7. INV-7: Every factual claim has an active policy ID, version, and matching evidence quote.
  8. INV-8: An unclear send or expired sending lease becomes uncertain and is never retried automatically.
  9. INV-9: The private worker accepts only IAM-authenticated Cloud Tasks and Cloud Scheduler calls.
  10. INV-10: Secrets never appear in stored request data, model prompts, or logs.
  11. INV-11: One atomic request lease and one atomic delivery lease control concurrent workers.
  12. INV-12: Only one approved policy version can be active for a stable policy ID.
  13. INV-13: The retention job removes stored message text and evidence quotes after the approved period.

Definition of done

Acceptance criteria

  1. AC-1: Slack URL verification succeeds against the deployed ingress.
  2. AC-2: Invalid, missing, and stale Slack signatures are rejected.
  3. AC-3: The ingress stores and acknowledges a valid event within three seconds.
  4. AC-4: Repeated events and duplicate workers do not create a second request or automatic reply.
  5. AC-5: A supported question receives a short answer whose factual claims map to active versioned evidence.
  6. AC-6: An off-topic question receives the fixed refusal.
  7. AC-7: A sensitive, unclear, or unsupported question receives the fixed referral.
  8. AC-8: A route timeout or invalid route does not reach retrieval or answer generation.
  9. AC-9: An expired request lease requeues below five attempts. At five attempts, infrastructure work reaches review.
  10. AC-10: Before retention runs, one completed request shows state, attempts, evidence, latency, usage, cost, and Slack reply ID. After retention, only approved metadata remains.
  11. AC-11: The full system works locally with a manual worker and on Google Cloud with Cloud Tasks.
  12. AC-12: A committed request reaches the worker after the first Cloud Tasks creation fails.
  13. AC-13: An unclear Slack API result becomes uncertain and cannot send again without operator review.
  14. AC-14: The daily retention job removes expired text, preserves allowed metrics, and reports a failed cleanup.
  15. AC-15: Exhausted answer-model attempts create the fixed referral. A failed referral delivery reaches review.
  16. AC-16: Cloud Scheduler invokes dispatch, sweep, and retention through authenticated private routes.

14 · Review before tickets

Six choices still need customer or live-system proof.

Blocks production

Unclear Slack delivery

Post a request ID as Slack message metadata. Prove that thread history can reconcile an unclear result. Until proved, uncertain delivery stops for operator review and never retries itself.

Default: #people-help

Human referral route

The customer must approve the exact channel, email address, and fixed referral text before launch.

Default: 30 days

Question retention

The customer must approve how long question text, model output, and evidence remain stored.

Default: message.channels

Slack event subscription

Use new top-level messages in one configured public channel. Direct messages, mentions, edits, files, and thread follow-ups stay outside version one.

Blocks production

Model provider data terms

The customer must approve whether question text can reach OpenAI, plus the provider retention, data region, and contract.

Default: private import

Policy owner and source

The customer must name who approves a policy and where production files live. The public repository contains sample policies only.

Proof for hard failures

Test the dangerous timing gaps.

Before delivery starts: a crash before the sending state is stored leaves delivery pending, so a later worker can send it.

During delivery: any crash after sending is stored becomes uncertain when its lease ends, even if the Slack call did not start.

After Slack replies: a crash before the database update becomes uncertain and needs thread reconciliation.
