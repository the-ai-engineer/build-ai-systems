System design · 11 August 2026

HR policy assistant for Slack

This document defines a Slack assistant that answers HR policy questions from approved documents. It sends unsafe or unclear questions to a person.

Python Slack Postgres Google Cloud

Design principle

The AI model is one component.

The application must receive and store requests. It must use approved data, handle failures, and record each result.

Status: ready for design review. No application code is approved by this document yet.

1 · Product outcome

What the system does

Today

Employees email HR with the same policy questions.

HR searches documents and writes each reply by hand.

Simple questions wait beside sensitive cases.

With this system

An employee asks a general policy question in #ask-hr.

The assistant replies in the thread from an approved policy.

Off-topic, sensitive, and unsupported questions go to HR.

A successful answer

“You can carry up to five unused days into the next holiday year with manager approval.”

Source: Annual Leave Policy, “Carrying leave forward”

2 · Product boundary

Scope for version 1

Version one serves one company, one Slack workspace, and one public HR channel. It handles new top-level text messages only.

It can

  • Answer general policy questions.
  • Name the policy used.
  • Refuse unrelated questions.
  • Refer unclear or sensitive cases.
  • Keep a record of each result.

It cannot

  • Read employee records.
  • Calculate personal entitlement.
  • Approve leave or expenses.
  • Handle private cases.
  • Answer from general model knowledge.

3 · Synchronous and asynchronous work

Request handling and background work

Slack expects an HTTP success response within three seconds. Model calls and document checks can take longer, so they run after the event is stored.

Synchronous · under 3 seconds

Slack waits
  1. 1Check Slack's signature and timestamp.
  2. 2Validate the event shape and channel.
  3. 3Store the event, request, and queue intent in one transaction.
  4. 4Try for one second to create a named Cloud Task, then return HTTP 200. The saved outbox repairs a failed task creation.

Asynchronous · background

Slack is free
  1. 1Cloud Tasks starts the worker. A scheduled dispatcher repairs only missed task creation.
  2. 2One worker gets a time-limited claim on the request. This claim is called a lease.
  3. 3The worker chooses a route, loads policies, and checks the evidence.
  4. 4A separate delivery lease controls the Slack reply.

4 · System context

System architecture

The public service accepts Slack events. It saves each request and tries to create a named Cloud Task at once. It cannot call the model or post answers. A scheduled dispatcher reads the outbox and repairs only missed task creation. The private worker runs the remaining steps.

Repair and maintenance

Cloud Scheduler signs each request with a Google identity. It calls /internal/dispatch each minute to repair pending outbox rows, /internal/sweep every five minutes, and /internal/retention each day. Normal requests do not wait for the dispatcher.

Local commands

Developers can run the same jobs once with python -m build_ai_systems.ops dispatch --once, sweep --once, or retention --once. The HTTP routes and commands call the same application functions.

What happens when 1,000 questions arrive

1. Store the work.
Cloud Tasks keeps every accepted request until the worker has space.

2. Limit the flow.
Start with 10 dispatches each second and 20 tasks running at once. Tune these limits after a load test.

3. Scale the workers.
Cloud Run adds instances up to its set limit. Extra tasks wait instead of overloading Vertex AI or Postgres.

If one task takes 10 seconds, 20 worker slots finish about two tasks each second. A burst of 1,000 tasks then takes about eight minutes. This is an example, not a service promise.

6 · Safety design

Request routing and safety rules

The model cannot use any tool it wants. Application code controls each step and stores the fixed refusal and referral messages.

The course still teaches agent loops. This application uses a fixed workflow because it has one job and known business rules.

7 · RAG choice

Load all approved policies for version 1

Retrieval-augmented generation, or RAG, means adding trusted information to the model request. Version one loads every active policy because the approved collection is small.

Chosen now

Small-set loading

Load one approved active version of each policy from Postgres. Recheck those versions before delivery.

Guardrail

Maximum policy size

Use the model's token counter. Refer the question to HR when the policies use more than 12,000 tokens. Do not drop a policy to make the input fit.

Later

Hybrid search

Add keyword and vector search only when the policy set becomes too large. Teach that deeper path in The Vault.

Active policies

approved versions only

→

Grounded answer

answer + policy IDs + quotes

Code checks proof

then Slack receives it

An exact quote proves that the source text exists. It does not prove that the claim is correct. A fixed evaluation set must test whether each answer follows from its evidence. Policy conflicts, missing evidence, and policy changes before delivery all produce a referral.

8 · Main decisions

Technical decisions

Fixed workflow

Application code controls the order of the steps. The model cannot add steps or choose other tools.

Cloud Tasks and Cloud Run

One outbox row creates one HTTP request to the private Cloud Run worker. The public service normally creates it at once. The dispatcher repairs failures. We reject Cloud Run Jobs because each Slack question is short, separate work. Jobs remain useful for long policy imports and evaluation runs.

Postgres stores system state

Cloud Tasks wakes the worker. Postgres stores queued work, leases, request state, attempts, evidence, and delivery state.

Two Cloud Run services

The public service accepts Slack events. The private worker can call the model, use the database, and reply in Slack. Google Cloud identity and access management, or IAM, keeps the worker private.

Gemini on Vertex AI

This companion application uses a generally available Gemini Flash model through Vertex AI. The exact model ID is deployment config and is stored with every result. Cloud Run uses its Google identity instead of an API key. The application requires replies with fixed data fields. Earlier provider lessons can still compare OpenAI and other models.

Small, controlled burst

Start with 10 task dispatches each second, 20 tasks at once, Cloud Run concurrency 4, and 5 worker instances. These teaching defaults protect Vertex AI and Postgres. Load tests decide whether to raise them.

Private policy import

A command validates approved Markdown from a private customer source and publishes it in one transaction. Real policies never enter this public repository.

9 · Components and data

Database tables

The database keeps business state. Logs help operators find problems, but logs are not the source of truth.

slack_events

Slack event ID, workspace, channel, user, message time, raw body hash, and received time. The event ID is unique.

support_requests

Request ID, question text, state, route, reason, model, prompt version, usage, latency, lease owner, and lease expiry.

dispatch_outbox

Request ID, dispatch number, unique task name, state, attempts, next dispatch time, and last safe error code. It is written with the request.

outbound_deliveries

One row per request with pending, sending, sent, or uncertain, plus a delivery lease, Slack metadata ID, and Slack message time. Only pending can start a send. An expired sending lease becomes uncertain.

policy_documents

Stable policy ID, version, content, content hash, approver, approval time, and active state. A database rule permits one approved active version per policy.

answer_evidence

Request ID, policy ID, policy version, and the exact supporting quote returned by the model.

processing_attempts

Step name, attempt number for that step, start and end time, outcome, safe error code, provider status, and retry choice. Worker, route-model, and answer-model attempts use separate counters. Secrets and raw model prompts stay out of logs.

All policy changes succeed together or none are saved. The import command checks every file before it changes an active version. A failed import changes nothing. Evidence keeps the exact version used. Example policies can live in this public repository. Real customer policies must come from a private approved source.

10 · Failure and recovery

Retries and duplicate prevention

Slack, Cloud Tasks, and Vertex AI can fail. Each retry has one owner and one limit. Every repeated step must be safe to run again.

↓

queued

↓

processing

worker retries at most 5 times

answered
refused
referred
needs review

Duplicate event

The unique Slack event ID returns the saved result. It does not create new work.

Task creation fails

The public service tries to create the named task for one second. A failure leaves the outbox row pending. A private dispatcher repairs it within one minute. The task name combines request ID and dispatch number. ALREADY_EXISTS counts as success only for that same outbox row.

Reply result is unclear

A timeout, unclear response, process crash, or expired sending lease becomes uncertain. It never returns to pending. Check the Slack thread. If the message cannot be found, a person must review the request.

Worker lease

One database update gives a worker a 120-second lease. The worker renews the lease between steps and must finish within 90 seconds. A second worker does nothing while the lease is active.

Stale work

The system queues the request again when its worker lease expires before attempt five. At attempt five it moves the request to needs_review. A request that waits for 20 minutes also moves to review.

Worker retry limit

Worker leases and Cloud Tasks transport retries are separate from model retries. The application stops after five expired worker leases. An extra task returns HTTP 204 and does no work.

Temporary Gemini failure

The application owns model retries, so the SDK must not add more. Retry HTTP 429, 500, 502, 503, 504, a connection failure, or a timeout at most two times. Wait at least one second, then double the delay and add random jitter. The initial call plus two retries gives three attempts for one model step.

Permanent Gemini failure

Do not retry HTTP 400, 403, or 404. Record a safe error code, alert the operator, and use the fixed referral. After temporary retries are used, also use the fixed referral. Return success to Cloud Tasks only after the referral is sent or its delivery is uncertain. A clear Slack or infrastructure failure remains retryable or moves to needs_review under the delivery rules.

Operator recovery

A command-line tool lists stuck requests, uncertain deliveries, failed tasks, and failed text deletion jobs. A person can inspect one request, mark a confirmed Slack message as sent, or queue safe work again. The tool never clears an active lease. It never changes uncertain delivery to pending.

11 · Security, privacy, and limits

Security, privacy, and limits

The system sends a fixed referral when it cannot verify the user, request scope, policy evidence, or Slack delivery.

Verify Slack requests

Check Slack's request signature against the original request body. Reject requests more than five minutes old.

Accept only supported messages

Require the configured workspace and channel, a human user, and a new top-level text message. Ignore bots, edits, deletes, files, and thread replies.

Limit access

The public service can store requests, write outbox rows, and create named tasks in one queue. It gets only the task enqueuer role and permission to use the task caller identity. It cannot call Vertex AI or post to Slack. The private worker can call Vertex AI and Slack.

Check private callers

Cloud Run IAM protects the whole private service, not each route. The task route checks for the Cloud Tasks service account. Repair, sweep, and retention routes check for the Cloud Scheduler service account. A valid identity on the wrong route is rejected.

Protect credentials

Cloud Run uses its service identity for Vertex AI. Store the Slack signing secret and bot token in Secret Manager. Never write credentials to Postgres, logs, or model prompts.

Delete message text after 30 days

A daily private job removes question text, answer text, and evidence quotes after 30 days. It keeps IDs, states, timings, policy versions, usage, and cost.

Data stored by Slack and Vertex AI

Logs do not contain message text. Slack and Vertex AI handle data under their own rules. The customer must approve those rules, the model location, and the Google Cloud project before production use.

Limit model work

Each request can make at most two logical model calls: route and answer. Each attempt stops after 10 seconds. Each logical call allows one initial attempt and two retries. Answers can contain at most 1,200 characters.

Limit queued work

Cloud Tasks starts at 10 dispatches each second and 20 tasks at once. Cloud Run starts at concurrency 4 and 5 worker instances. Warn when the oldest task waits for more than 10 minutes or the queue makes no progress for two minutes.

Record usage and cost

Record the model name, token count, response time, and estimated cost for each completed request.

12 · Build plan

Implementation plan

Each phase ends with a working result and a check. A phase must pass its check before the next phase starts.

Phase 1

Application setup

Python package, settings, Postgres tables, Vertex AI model config, local Google credentials, local commands, and health checks.

Check: create a clean local database and make one structured Gemini call.

Phase 2

Public Slack service

Slack URL check, request signature check, supported message filter, and one database save.

Check: store each valid human message once. Reject or ignore every unsupported message.

Phase 3

Background work

Immediate Cloud Task creation, outbox repair, queue limits, leases, retries, stale-work checks, and manual requeue.

Check: normal work starts without waiting for the scheduler. A failed task creation is repaired within one minute.

Phase 4

Scope and referral

Gemini structured route fields, refusal text, referral text, temporary error retries, and permanent error handling.

Check: off-topic and unsafe questions never reach answer generation. Model errors follow the stated retry rule.

Phase 5

Trusted policy answers

Policy import, maximum token count, fixed claim fields, conflict checks, and evidence checks.

Check: every factual claim links to approved evidence and passes the test cases.

Phase 6

Slack delivery

Delivery record, delivery lease, message ID, thread check, and Slack rate limits.

Check: an unclear delivery never causes a second automatic reply.

Phase 7

Tests and operations

Fixed test cases, logs, model usage, cost, text deletion, and a command-line recovery tool.

Check: explain one complete request and test a recovery command for every failure state.

Phase 8

Google Cloud deployment

Cloud Run, Cloud Tasks, Cloud Scheduler, Cloud SQL, Vertex AI, Secret Manager, access rules, live Slack, and failure tests.

Check: test task creation failure, Gemini 429 and 5XX errors, queue limits, two workers, unclear delivery, and recovery.

13 · Rules that must stay true

Invariants

  1. INV-1: No Slack event can create work before its signature and timestamp pass.
  2. INV-2: The event, request, and outbox row are saved together before the public service returns success.
  3. INV-3: One Slack event ID maps to one support request.
  4. INV-4: The model cannot call Slack, Postgres, or Cloud Tasks.
  5. INV-5: Off-topic requests do not load policies or generate answers.
  6. INV-6: An invalid route, route timeout, invalid evidence data, or evidence conflict becomes a human referral.
  7. INV-7: Every factual claim has an active policy ID, version, and matching evidence quote.
  8. INV-8: An unclear send or expired sending lease becomes uncertain and is never retried automatically.
  9. INV-9: Each private route accepts only its expected Cloud Tasks or Cloud Scheduler service account.
  10. INV-10: Secrets never appear in stored request data, model prompts, or logs.
  11. INV-11: One database update grants the request lease. Another database update grants the delivery lease.
  12. INV-12: Only one approved policy version can be active for a stable policy ID.
  13. INV-13: The retention job removes stored message text and evidence quotes after the approved period.
  14. INV-14: A model step makes at most three attempts and retries only temporary provider or network errors.
  15. INV-15: Cloud Tasks limits how quickly work reaches Vertex AI and Postgres.

Definition of done

Acceptance criteria

  1. AC-1: Slack's URL check succeeds against the deployed public service.
  2. AC-2: Invalid, missing, and stale Slack signatures are rejected.
  3. AC-3: The public service stores and accepts a valid event within three seconds.
  4. AC-4: Repeated events and duplicate workers do not create a second request or automatic reply.
  5. AC-5: A supported question receives a short answer whose factual claims map to active versioned evidence.
  6. AC-6: An off-topic question receives the fixed refusal.
  7. AC-7: A sensitive, unclear, or unsupported question receives the fixed referral.
  8. AC-8: A route timeout or invalid route does not load policies or generate an answer.
  9. AC-9: If a worker lease expires before attempt five, the system queues the request again. At attempt five, it sends the request for review.
  10. AC-10: Before text deletion, a completed request shows its state, attempts, evidence, response time, usage, cost, and Slack reply ID. After deletion, only approved system data remains.
  11. AC-11: The full system works locally with a manual worker and on Google Cloud with Cloud Tasks.
  12. AC-12: A committed request reaches the worker within one minute after the immediate Cloud Task creation fails.
  13. AC-13: An unclear Slack API result becomes uncertain and cannot send again without operator review.
  14. AC-14: The daily retention job removes expired text, preserves allowed metrics, and reports a failed cleanup.
  15. AC-15: A model step retries a temporary failure at most twice. A permanent failure or three failed attempts produce the fixed referral and an operator alert. Cloud Tasks receives success only after referral delivery is sent or uncertain.
  16. AC-16: Cloud Scheduler invokes repair, sweep, and retention through authenticated private routes. Normal work does not wait for the repair job.
  17. AC-17: A fake-model load test accepts 1,000 requests, never runs more than 20 worker tasks at once, loses no request, and drains the queue.
  18. AC-18: Cloud Tasks cannot call maintenance routes, Cloud Scheduler cannot call the task route, and an unknown service account cannot call any private route.

14 · Open questions

Open questions before production

Blocks production

Unclear Slack delivery

Add the request ID to the Slack message data. Search the thread for that ID after an unclear result. If the message cannot be found, a person must review the request. The system must not send it again.

Default: #people-help

Human referral route

The customer must approve the exact channel, email address, and fixed referral text before launch.

Default: 30 days

How long message text is kept

The customer must approve how long the system keeps question text, model output, and evidence.

Default: message.channels

Slack messages the app receives

Accept new top-level messages in one public channel. Do not accept direct messages, mentions, edits, files, or thread replies in version one.

Blocks production

Vertex AI data rules

The customer must approve sending question text to Vertex AI. The customer must also approve the Google Cloud project, model location, data rules, and contract.

Default: private import

Policy owner and source

The customer must name who approves a policy and where production files live. The public repository contains sample policies only.

Required failure tests

Slack delivery crash tests

Before delivery starts: a crash before the sending state is stored leaves delivery pending, so a later worker can send it.

During delivery: any crash after sending is stored becomes uncertain when its lease ends, even if the Slack call did not start.

After Slack replies: a crash before the database update becomes uncertain and needs thread reconciliation.
